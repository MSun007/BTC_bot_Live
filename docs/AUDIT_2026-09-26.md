The audit inspected the public GitHub source, the source files actually on the paper VM, systemd health, VM status, Cloud Run traffic, Cloud Scheduler/watchdog configuration, recent Cloud Logging failures, and the authenticated dashboard. ## Evidence and confidence

At inspection the paper service was active, its restart counter was zero, the VM had ample disk space, the paper snapshot was fresh and its notification queue empty. Both historical trading VMs were stopped. All observed dashboard 5xx requests in the seven-day query were to `/api/paper-health` (67 records); no `/api/data` 5xx appeared in that query. One recent engine market-data disconnect appeared in the available VM journal and recovered.

The read race is reproduced in fault-injection tests. A short direct production read probe did not encounter a failure. Historical health responses suppressed the cause, so the race is a credible defect and explanation, **not proof that every historical 503 or Telegram alert had that cause**. Exact Telegram examples are needed for message-level attribution.

Pre-change suites: GitHub risk suite 52 tests; recovered paper distribution 69 tests. The expanded local suite passes 99 tests. Added tests cover flat position truth, funding reconciliation, snapshot races, error/stale health, failed-cycle notification delivery, committed fills surviving publication failure, fixed dashboard controls, profile startup integrity, proportional paper scaling, monitor debounce/persistence and failed-delivery backoff.

The fresh local dependency resolution was checked with pip-audit and returned no known vulnerabilities. Runtime dependency ranges are not reproducible pins, and deployed package versions were not exhaustively audited. Syntax checks cover all top-level Python and the rendered dashboard JavaScript; static analysis checks undefined names and syntax-related errors. Passing checks do not certify all execution paths or future uptime.

## Remaining work before claiming unattended reliability

1. Funding gaps currently block the whole cycle with open exposure, including exits. A reviewed historical-rate reconciliation workflow is still required.
2. Notification delivery now has a three-message cap, a ten-second soft budget between sender calls and exponential failure backoff. A single bounded sender call can exceed the soft budget. Production outage behavior still needs observation.
3. Monitor alerts now include reasons, ages and queue counts, with two-check transient-error/recovery debounce and hourly reminders. Stale engine data bypasses debounce. Production observation is still needed to assess alert quality.
4. Trade statistics allocate historical entry fees evenly across realized exit events, not actual closed lots. Sparse realized-event Sharpe is not a daily mark-to-market Sharpe. Do not present it as institutional performance reporting.
5. Legacy helper `pair_scan.py` aligns return vectors by array position rather than timestamp. It is not used by the bot. Do not rely on cross-asset correlations from series with missing dates until it is repaired.
6. Snapshot size grows with the full account fill history and stored objects; no long-duration size/performance test was performed.
7. Keep provenance visible: the old UI version banner does not distinguish paper adapter releases. The source manifest records the observed pre-audit package, not the new patched files.
8. Full IAM/firewall/secret-history audit, container scanning, failure-injection deployment tests, backup restore rehearsal and $10k end-to-end replay remain unverified.
9. The external watchdog stores state in the same bucket it monitors. All failures now produce a sanitized error log and unsuccessful job exit, but a bucket-wide outage can prevent Telegram alert delivery. An independent Cloud Monitoring error-log policy now routes watchdog/job/scheduler failures to Larry's existing email destination. Inbox delivery and missing-execution detection have not been verified.
